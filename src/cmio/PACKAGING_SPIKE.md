## 1. Packaging and activation

**Bundle layout [doc].** The extension ships *inside* the app: "System extensions reside inside your app's `Contents/Library/SystemExtensions` folder." Activation verifies, among other things, that "Your extension is installed in the `Contents/Library/SystemExtensions` folder of your app", "Your app is installed in an appropriate `Applications` directory of the system", "The code signature of your extension", "The entitlements in the code signature match the entitlements granted to your development team", and that the identifier is unique. — https://developer.apple.com/documentation/systemextensions/installing-system-extensions-and-drivers

**Camera-extension specifics [doc].** "Only apps that reside in the `/Applications` directory can activate an extension. To test your extension, move your app from Xcode's build results to the `/Applications` folder." and "Before the extension is available to the system, a person with Admin privileges for the Mac must explicitly allow access to it". Camera extensions exist since macOS 12.3. — https://developer.apple.com/documentation/coremediaio/creating-a-camera-extension-with-core-media-i-o

**Naming/signing rules for the sysext bundle [doc].** "The extension must match your bundle identifier, excluding file extension" (i.e. `com.example.foo.systemextension`); "You must use the same Team ID when signing the extension that you use for signing your app"; "You must either distribute your app and extension through the Mac App Store, or notarize them." — https://developer.apple.com/documentation/systemextensions

**Activation API [doc].** `OSSystemExtensionRequest.activationRequest(forExtensionWithIdentifier:queue:)` → `OSSystemExtensionManager.shared.submitRequest(_:)`; delegate gets `requestNeedsUserApproval`, `didFailWithError`, and `actionForReplacingExtension(_:withExtension:)` for version upgrades. Uninstall = deactivation request, or the system removes it when the app is deleted. (same two URLs as above)

**Info.plist contract [doc/src].** WWDC22: "The Info.plist identifies it as a CMIOExtension by defining its MachServiceName. This is a critical piece of information. CoreMedia IO's registerassistant will not launch your extension unless it's present." and "I need to ensure here that my extension's app group is prefixed by the MachServiceName in order for it to pass validation." — https://developer.apple.com/videos/play/wwdc2022/10022/ . OBS's actual plist **[src]**: `CMIOExtension → CMIOExtensionMachServiceName = $(TeamIdentifierPrefix)$(PRODUCT_BUNDLE_IDENTIFIER)` — https://raw.githubusercontent.com/obsproject/obs-studio/master/plugins/mac-virtualcam/src/camera-extension/cmake/macos/Info.plist.in . Getting this prefix wrong yields `OSSystemExtensionErrorDomain Code=9` (ValidationFailed) **[forum]** — https://developer.apple.com/forums/thread/705552 (fix: "I didn't prefix my Mach service name with the name of the app group in my entitlement"; diagnose from `sysextd` logs, not app logs).

**Runtime identity [doc].** The extension is launched by `registerassistantservice` "as a role user account called `_cmiodalassistants`" and "must be app sandboxed, or it won't be allowed to run"; sandbox profile forbids fork/exec/posix_spawn, the window server, connecting to the foreground user account, and registering global mach services; it allows USB/Bluetooth/Wi-Fi client access and read/write to its own container and tmp. — WWDC22 10022 (URL above).

**Approval UI by OS version.**
- ≤ macOS 14: System Settings → Privacy & Security **[doc]** https://support.apple.com/en-us/120363
- macOS 15 Sequoia: moved to **General → Login Items & Extensions** ("For macOS Sequoia 15 or later: Login Items & Extensions settings") **[doc]** same URL; Sequoia also lets admins *disable* extensions from that pane (MDM keys `NonRemovableFromUISystemExtensions` etc. exist to stop that) **[3p]** https://www.jamf.com/blog/system-extension-changes-in-sequoia/ ; OBS users confirm the Camera Extensions sub-pane **[3p]** https://obsproject.com/forum/threads/macos-15-sequoia-beta-system-extensions-settings-moved.176958/
- macOS 26 Tahoe: **conflicting reports.** Apple's Tahoe-era Mac Help still lists "Camera extensions" under Login Items & Extensions **[doc]** https://support.apple.com/guide/mac-help/change-login-items-extensions-settings-mtusr003/mac ; and on this machine (26.6.2) `systemextensionsctl` itself points at `General > Login Items & Extensions > Camera Extensions` **[local]**. An OBS forum thread for 26.3.1 claims the toggle instead appears as a "Media Extension" under **Privacy & Security → Extensions** and that the Camera Extensions section is gone **[3p]** https://obsproject.com/forum/threads/virtual-camera-mac-os-tahoe-26-3-1.194658/ . Treat the local tool banner as authoritative and check both panes on the first activation; since OBS's extension is *already* sitting in `[activated waiting for user]` on this Mac, the owner can locate the pane today without building anything.
- Legacy DAL plug-ins stopped loading in macOS 14.1 ("only cameras and video output devices that use modern system extensions are supported") **[doc]** https://support.apple.com/en-us/108387 — the extension path is the only path.

**Iteration cost [3p].** Halle Winkler: "to see software changes in your extension, you currently have to uninstall the old extension using your container app, then reboot, then build and run your new container app iteration, then install the changed extension." — https://theoffcuts.org/posts/core-media-io-camera-extensions-part-one/ . Apple's supported update path is bump the version and let `actionForReplacingExtension` replace it **[doc]** (installing doc above). Developer mode skips the version check (`systemextensionsctl` man page: "When developer mode is on, this version check is skipped") **[doc]** https://keith.github.io/xcode-man-pages/systemextensionsctl.8.html . Her recommended loop is to also build a plain macOS app target that instantiates the provider class directly so most logic iterates without touching sysextd **[3p]** https://theoffcuts.org/posts/core-media-io-camera-extensions-part-two/ .

## 2. Entitlements, signing, developer mode

**Host app entitlements [doc].** Apple's example: `com.apple.security.app-sandbox`, `com.apple.developer.system-extension.install`, `com.apple.security.application-groups = [$(TeamIdentifierPrefix)com.example.CustomCamera]`. The sandbox entitlement on the *app* is in Apple's example but not stated as mandatory; OBS.app is a non-sandboxed host **[src, inferred from OBS being non-sandboxed]**. — creating-a-camera-extension URL (§1); entitlement page: "Add this entitlement for all system extension types" https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.system-extension.install

**Extension entitlements [doc/src].** Mandatory `com.apple.security.app-sandbox = true` plus the same app group. OBS's real file is exactly those two keys **[src]** https://raw.githubusercontent.com/obsproject/obs-studio/master/plugins/mac-virtualcam/src/camera-extension/cmake/macos/entitlements.plist . `com.apple.security.device.usb` ("allow your sandboxed app to interact with USB devices through USB device access APIs") is only needed if USB is touched *inside* the extension **[doc]** https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.device.usb — our design (§10) keeps USB in the service, so the extension does not need it. `com.apple.security.device.camera` is only for extensions that *consume* another camera **[doc, WWDC22]**.

**Which entitlements need a provisioning profile (this is the crux) [doc].** TN3125: on macOS, *unrestricted* entitlements need no profile: `get-task-allow`, `application-groups`, App Sandbox keys, Hardened Runtime keys. "In contrast, restricted entitlements must be authorized by a provisioning profile." and "A Mac app that uses no restricted entitlements doesn't need a provisioning profile." — https://developer.apple.com/documentation/technotes/tn3125-inside-code-signing-provisioning-profiles . `system-extension.install` is not on the unrestricted list ⇒ the **host app needs an embedded provisioning profile** (`Contents/embedded.provisionprofile`) carrying the System Extension capability **[inferred from TN3125 + the activation check "entitlements … match the entitlements granted to your development team"]**. The **extension** itself only claims sandbox + app groups ⇒ no profile strictly required for the extension **[inferred from TN3125]**; note a Developer-ID shipping case where DTS-guided debugging ended with profiles for *both* app and extension **[forum]** https://developer.apple.com/forums/thread/736838 — harmless to add both.

**Is a paid membership required? YES for a SIP-on machine [doc].** Apple's capability matrix for macOS: the row **"System Extension" is checked for ADP (paid) and Developer ID, and EMPTY for the free "Apple Developer" tier** (parsed from the page markup: `<figure class="icon icon-checksolid" alt="yes">` in the first two columns, empty `<td>` in the third); "App groups" and "Hardened runtime" are available to all three; "DriverKit Family MIDI" is paid-only too. Legend: "ADP: Apple Developer Program membership. Members of this paid program can distribute apps on the App Store." — https://developer.apple.com/help/account/reference/supported-capabilities-macos/ . Corroboration **[forum]**: OBS builders hit "Missing entitlement com.apple.developer.system-extension.install" until they switched to automatic signing with a (paid) team ID — https://developer.apple.com/forums/thread/793731 ; OBS's PR: the extension is *disabled* unless the signing/provisioning triplet is provided, so unsigned CI builds carry no working virtual camera — https://github.com/obsproject/obs-studio/pull/7777 . Quinn, on free accounts generally: "Only Developer ID signed code can pass Gatekeeper … [that] requires a paid account" — https://developer.apple.com/forums/thread/712555 .

⇒ **On this Mac today** the only Xcode-registered team is a free Personal Team, which cannot carry the System Extension capability; the `<other-team-id>` identity in the keychain belongs to some other team whose membership status I could not determine offline **[local]**. See "Blockers".

**What `systemextensionsctl developer on` does and does not do [doc].** Apple's page has two *separate* sections: (a) "Enable activation from any directory … use the `systemextensionsctl` command-line tool to enable developer mode. When in developer mode, the system doesn't check the location of your system extension prior to loading it, so you can load it from anywhere in the file system." (b) "Disable code-signing and notarization checks — … Xcode doesn't notarize apps or system extensions during the normal development cycle, so disabling SIP bypasses the notarization checks that the system normally performs". — https://developer.apple.com/documentation/driverkit/debugging-and-testing-system-extensions . Plus the man page: developer mode skips the version-equality check **[doc]**. So: developer mode relaxes **location and version** only; it does **not** waive signing/entitlement validation — that waiver is tied to SIP-off, which this project forbids. Whether the `developer on` *toggle itself* requires SIP off is **not stated in Apple's docs**; a search summary asserted it but cited no primary source, and I did not toggle it here (state change). The doc's structure implies it works with SIP on **[inferred]**. Apple's audio-dext sample confirms the SIP-off route is what makes *ad-hoc-signed* system extensions load ("Disable System Integrity Protection (SIP) on your system so it recognizes ad hoc-signed DriverKit extensions") **[doc]** https://developer.apple.com/documentation/coreaudio/building-an-audio-server-plug-in-and-driver-extension — i.e. with SIP on, an unsigned/ad-hoc/unprovisioned extension has no path to activation. Forum symptom of exactly that: loads with SIP off + developer on, fails (`[validating by category]`) with SIP on + developer off **[forum]** https://developer.apple.com/forums/thread/764939 .

**Day-to-day dev signing [forum].** Quinn: use Apple Development credentials for day-to-day development and reserve Developer ID for shipping; don't `codesign --deep` — https://developer.apple.com/forums/thread/736838 and /793731. Error code map: `8 = OSSystemExtensionErrorCodeSignatureInvalid` ("Invalid code signature or missing entitlements"), `9 = ValidationFailed` (typically the Mach-service/app-group prefix) **[forum]** threads 736838, 705552.

## 3. Notarization

- **Required for distribution, not for local development [doc].** SystemExtensions: "You must either distribute your app and extension through the Mac App Store, or notarize them." Notarization doc: "Beginning in macOS 10.15, all software built after June 1, 2019, and distributed with Developer ID must be notarized." Notarization "is not App Review". — https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution . Xcode dev builds run on the build machine without notarization ("Xcode doesn't notarize apps or system extensions during the normal development cycle") **[doc]** debugging URL above; OBS: "When not compiled on your own machine, the app also needs to be notarised" **[3p/src]** PR 7777.
- **Sequoia+ tightening [doc].** Users can no longer Control-click to override Gatekeeper for unsigned/un-notarized software; they must go to Privacy & Security — https://developer.apple.com/news/?id=saqachfa .
- **Requirements [doc].** Developer ID Application certificate ("Don't use a Mac Distribution, ad hoc, Apple Developer, or local development certificate"), **Hardened Runtime** on app and command-line targets, secure timestamp (`--timestamp`; only `timestamp.apple.com`), no `get-task-allow`, SDK ≥ 10.9, well-formed entitlements. Tooling: `notarytool` (altool/Xcode ≤13 rejected since 2023-11-01); flow = archive → Distribute App → Developer ID → Upload, or `xcrun notarytool submit --wait` then `xcrun stapler staple`. — notarizing URL + https://developer.apple.com/documentation/security/resolving-common-notarization-issues
- **Hardened-runtime implication for this project [inferred].** Library validation under hardened runtime rejects dylibs not signed by the same Team ID or Apple. The libusb 1.0.30 from Homebrew is ad-hoc signed, so for a shippable build the service must **bundle its own libusb inside the app and re-sign it with the team identity** (or, worse, claim `com.apple.security.cs.disable-library-validation`). Same for any Homebrew ffmpeg pieces if ever linked. Not an issue for local dev builds. Apple mentions the disable-library-validation escape hatch for camera-driver plug-ins **[doc]** (notarizing URL, "Notarize plug-ins").

## 4. Architecture: video-only extension, out-of-process feeder, audio side

**Video-only [doc + inferred].** Every Apple description is camera-shaped: `CMIOExtensionDevice` "represents a hardware or software device that the extension publishes as a selectable camera in apps like FaceTime"; the API surface (Provider / Device / Stream with source/sink direction, `CMIOExtensionStreamFormat(formatDescription:maxFrameDuration:minFrameDuration:validFrameDurations:)`, `send(_:discontinuity:hostTimeInNanoseconds:)`) has no audio-device or audio-stream type — https://developer.apple.com/documentation/coremediaio/cmioextensionstream , /cmioextensionstreamformat . No Apple document says audio is supported; "video-only" is the only reading consistent with the API **[inferred]**, and the project's §10 assumption stands.

**How frames get in from another process — Apple's answer is the SINK STREAM, not XPC [forum/doc].** Quinn: "the `CMIOExtensionMachServiceName` property is a red herring … It's not something you can use for XPC comms." and "our general advice is that you avoid XPC entirely" — split IPC into (1) command/control via **custom properties** and (2) "If you need to pass a video stream into your CMIO extension, have the CMIO extension publish an output device" — https://developer.apple.com/forums/thread/706184 (and ?page=2). The reason is structural: the extension runs as `_cmiodalassistants`, so a user-session mach service is not reachable from it ("failed at lookup with error 3") **[forum]** same thread; `Process.run()` is denied, DistributedNotificationCenter doesn't arrive, and the only hack that worked was the *extension* listening on a loopback TCP port **[forum]** https://developer.apple.com/forums/thread/742513 . WWDC22 defines the mechanism: "Clients feed your sink stream by inserting sample buffers into a simple queue. That translates to a consumeSampleBuffer call in your extension, and once you've consumed that buffer, you notify them with notifyScheduledOutputChanged" and "output devices have no AVFoundation API equivalent. To send frames to an output device, you must use the CoreMedia IO C API directly." **[doc]** WWDC22 10022.

**Proof it works out-of-process, with zero-copy [src].** OBS: the *app side* enumerates `kCMIOHardwarePropertyDevices`, matches the device UID from its Info.plist, `CMIOStreamCopyBufferQueue(streamID, …, &queue)`, `CMIODeviceStartStream(deviceID, streamID)`, allocates from a `CVPixelBufferPool` whose attributes include `kCVPixelBufferIOSurfacePropertiesKey` (so buffers are IOSurface-backed and cross the process boundary without copying), wraps each frame in a `CMSampleBuffer` with `presentationTimeStamp = CMTimeMake(frame->timestamp, NSEC_PER_SEC)`, and `CMSimpleQueueEnqueue(queue, sampleBuffer)`; formats offered: 420 planar, NV12 (420v), and `kCVPixelFormatType_422YpCbCr8` (2vuy) — https://raw.githubusercontent.com/obsproject/obs-studio/master/plugins/mac-virtualcam/src/obs-plugin/plugin-main.mm . The *extension side* consumes via `stream.consumeSampleBuffer(from: client)` and re-emits on its source stream (`sinkBufferQueueSize = 1`) — https://raw.githubusercontent.com/obsproject/obs-studio/master/plugins/mac-virtualcam/src/camera-extension/OBSCameraDeviceSource.swift and OBSCameraStreamSink.swift. Reference samples: https://github.com/ldenoue/cameraextension ("the sink stream is used by our own app to send frames to the virtual camera, which immediately forwards them to its source stream"), https://github.com/Halle/SinkCam .

**Consequences for this project [inferred, from the above]:**
1. The "one USB capture service" must be a **user-session process** (a LaunchAgent, or a helper embedded in the configurator app), because the sink stream is fed *from the login session toward the extension*; a root LaunchDaemon would be the wrong direction and unnecessary (libusb needs no root, §3). It pushes IOSurface-backed `2vuy` `CVPixelBuffer`s via the CMIO C API. This is exactly the §10 "IOSurface-backed shared frames" plan, with CMIO's own sink queue as the transport instead of a hand-rolled XPC channel.
2. Timing must be set explicitly: buffers need valid `CMSampleTimingInfo` against the host clock or clients show nothing/jitter (a developer who blamed pixel formats found "I wasn't setting the timing info right"; fix was `CMSampleBufferCreateCopyWithNewTiming` with `CMClockGetHostTimeClock()`) **[forum]** https://developer.apple.com/forums/thread/725481 . Our monotonic device-derived PTS (§9) must be mapped onto host time at the delivery edge.
3. Two advertised formats (raw 480i / corrected 480i, §10) map to two `CMIOExtensionStreamFormat`s on one source stream, or two devices; the feeder selects by a custom property. Custom properties are reachable only via the CMIO C API, not AVFoundation ("AVFoundation doesn't work with custom properties") **[doc]** WWDC22 — fine for the configurator app.
4. Restricting who may feed the sink: the extension sees a `CMIOExtensionClient` per connection and can refuse; WWDC22 says sink streams "can be restricted" **[doc]**; matching on the client's signing identity is the obvious policy **[inferred]**.
5. **Fallback if sink-stream latency/timing misbehaves:** the sandbox profile does allow USB from inside the extension (WWDC22) and `com.apple.security.device.usb` is a plain sandbox key; a developer opened a DriverKit user client from a camera extension after adding a temporary-exception entitlement **[forum, no Apple answer]** https://developer.apple.com/forums/thread/716181 . Cost: the capture core would then run as `_cmiodalassistants` with writes limited to its container/tmp (TPC debug sink constrained), no fork/exec, and Darwin libusb behaviour under that sandbox is untested. Keep it as a contingency only; it contradicts §10 and §8 property 10.

**Audio side — CoreAudio HAL plug-in (AudioServerPlugIn) [doc/3p/local].**
- Install: "Install the sample's `.driver` bundle to `/Library/Audio/Plug-Ins/HAL` and reboot" **[doc]** https://developer.apple.com/documentation/coreaudio/creating-an-audio-server-driver-plug-in . The directory is root-owned on this Mac **[local]** ⇒ installation needs admin/sudo (BlackHole ships a signed+notarized `.pkg` that needs an admin password and restarts coreaudiod; source builds "Copy or move the built `BlackHoleXch.driver` bundle to `/Library/Audio/Plug-Ins/HAL`" then `sudo killall -9 coreaudiod`) **[3p]** https://github.com/ExistentialAudio/BlackHole (README) ; BackgroundMusic: "copy `Background Music Device.driver` to `/Library/Audio/Plug-Ins/HAL` and restart coreaudiod", via `launchctl unload/load …coreaudiod.plist` **[3p]** https://github.com/kyleneideck/BackgroundMusic/blob/master/DEVELOPING.md . For this project the install step goes through the existing `sudo_run.sh` allow-list mechanism (owner's global rules) — no other privilege path.
- Runtime/sandbox: the plug-in is loaded into `coreaudiod` (root) and is sandboxed: it "may not make any calls to the client HAL API", may only read its own bundle plus system frameworks, may write only cache/tmp, and **may talk to other processes only through mach services listed under `AudioServerPlugIn_MachServices` in its Info.plist** **[doc]** https://developer.apple.com/library/archive/qa/qa1811/_index.html . So the audio path is: capture service exposes an XPC/mach service → HAL plug-in (listed in `AudioServerPlugIn_MachServices`) pulls 48 kHz PCM (BackgroundMusic's "XPC helper" pattern) **[3p + inferred]**. Real-time constraints: no allocation in IO paths **[3p]** BackgroundMusic.
- Signing: Apple's sample says nothing about signing; a 2021 security write-up claims unsigned HAL plug-ins load **[3p, undated for 26.x]** https://theevilbit.github.io/beyond/beyond_0013/ ; BlackHole is "signed and notarized by Apple" **[3p]**. On this OS three vendor HAL drivers are installed and (presumably signed) loading **[local]**. Whether an *unsigned* or Apple-Development-signed plug-in loads on 26.6 is **unverified** — testable in 5 minutes once a `.driver` exists (build Apple's sample, install, `system_profiler SPAudioDataType`). Expect at minimum a team-signed bundle; notarization only matters when distributed.
- Alternative rejected: AudioDriverKit needs DriverKit entitlements *requested from Apple* per device/transport **[doc]** https://developer.apple.com/documentation/driverkit/requesting-entitlements-for-driverkit-development — a review/approval process, not just money.
- OBS-specific alternative (already in §10): a native OBS source plugin carries video+audio in one source and needs neither the CMIO extension nor a HAL plug-in for the OBS use case **[inferred from OBS plugin model]**.

## 5. Client compatibility

**Pixel formats — no Apple list exists.** Neither the doc nor WWDC22 enumerates accepted formats; Xcode's template uses `kCVPixelFormatType_32BGRA` **[3p/forum]**. Evidence per client:
- **Chromium (Chrome, Edge, Electron, Meet/Teams-web) accepts 2vuy natively [src].** `FourCCToChromiumPixelFormat` maps `kCVPixelFormatType_422YpCbCr8` ("Mac fourcc: 2vuy") → `PIXEL_FORMAT_UYVY`, alongside 420v, 420f, yuvs, and MJPEG — https://raw.githubusercontent.com/chromium/chromium/main/media/capture/video/apple/video_capture_device_avfoundation.mm (lines ~285–305). Chromium picks the device format closest to the page's constraints and scales in libyuv, so a 720×480 format is selectable **[inferred from the same file's FindBestCaptureFormat]**.
- **OBS (mac-avcapture) accepts 2vuy as a first-class input [src]** (`kCVPixelFormatType_422YpCbCr8 → VIDEO_FORMAT_UYVY`, label "UYVY (2vuy)") — https://raw.githubusercontent.com/obsproject/obs-studio/master/plugins/mac-avcapture/OBSAVCapture.m . **It has no field/interlace handling at all** (zero hits for `field`/`interlac` in the file) ⇒ any field metadata is discarded; OBS treats frames as progressive and its per-source Deinterlacing menu is the user's tool, which matches §10's "OBS deinterlaces" decision.
- **QuickTime Player: only devices whose `.formats` include 32BGRA appeared; Photo Booth accepted 420v or 32BGRA; both then accepted sample buffers in a *different* format than advertised** ("Lesson: declare kCVPixelFormatType_32BGRA in .formats, and send whatever you want") **[forum, one developer's 2023 observation]** https://developer.apple.com/forums/thread/725481 . So a 2vuy-only format list risks *invisibility* in QuickTime; the cheap mitigation is to advertise a 32BGRA format alongside 2vuy (or verify QuickTime on 26.x first).
- **FaceTime / Safari / Zoom / Teams:** Apple: camera extensions are "automatically available as a selectable camera in system apps like FaceTime and PhotoBooth" and fully compatible with AVFoundation **[doc]**; ldenoue's sample reports working in "QuickTime, Zoom, Safari" **[3p]**; ManyCam notes their extension is "supported by a wider range of applications, including Safari and Photo Booth" than the old DAL plug-in **[3p]** https://help.manycam.com/knowledge-base/macos-camera-extension/ . **No public format matrix exists for Zoom/Teams/FaceTime** — they go through AVFoundation, which can convert, so 2vuy *probably* works **[inferred]**; must be measured.
- **Interlace / field metadata through CMIO: undocumented.** `kCVImageBufferFieldCountKey`/`FieldDetailKey` are CVPixelBuffer attachments and `kCMFormatDescriptionExtension_FieldCount/FieldDetail` are format-description extensions; whether either survives CMIO's IPC into an AVCaptureSession client's `CMSampleBuffer`/`AVCaptureDeviceFormat.formatDescription` is **not documented anywhere I found** **[inferred: must test]**. Even if they survive, no client above deinterlaces on them (OBS provably ignores them). Practical position: publish woven 720×480 frames at 29.97 fps, keep field order in a custom property + the decision log, and expect combing in every consumer that does not deinterlace — which is the §10 design.
- **Non-square pixels [inferred].** No AVFoundation client honours a pixel-aspect extension; a 720×480 stream displays as 3:2 (horizontally stretched 4:3) in Chrome/Zoom/FaceTime. Either accept that (archival correctness, §10 says both formats stay 720×480i) or add a presentation-only 640×480 format. This is a policy call — see Blockers.
- **Note from 725481 [forum]:** "the conversion to 32BGRA doubles my app's CPU usage" — at SD this is irrelevant, but it argues for feeding 2vuy and advertising 32BGRA only as a compatibility format if QuickTime needs it.

## 6. GPLv2+ and Apple platform constraints

- **No Apple rule against GPL for Developer-ID/notarized software found.** Notarization "is not App Review" **[doc]**; the well-known GPL/Apple conflict is about *App Store* terms ("you may not impose any further restrictions" vs. the App Store usage rules) **[3p]** https://www.fsf.org/blogs/licensing/more-about-the-app-store-gpl-enforcement — irrelevant to direct distribution.
- **Direct precedent:** OBS Studio is GPLv2 (`COPYING` = "GNU GENERAL PUBLIC LICENSE Version 2, June 1991" **[src]** https://raw.githubusercontent.com/obsproject/obs-studio/master/COPYING) and ships a Developer-ID-signed, notarized CMIO camera extension outside the App Store **[src/3p]** PR 7777. VLC and HandBrake are the same shape (GPL, Developer ID, notarized) **[3p, general knowledge — not re-verified this pass]**.
- **Signing keys vs GPLv2 [inferred, not legal advice]:** GPLv2 has no anti-tivoization clause (that is GPLv3 §6 "Installation Information"); a private Developer ID key does not have to be published for a GPLv2+ build to comply — users who rebuild from source must supply their own team/identity, exactly as OBS documents. The project's existing "GPLv2+ with NOTICE crediting bmusb" decision needs no change.
- **What it does cost:** the free tier cannot sign a sysext at all (§2), so an open-source project *must* hold a paid ADP membership to publish working binaries; contributors without one can build, but their builds will not activate with SIP on (OBS PR 7777 describes precisely this) **[src]**.
